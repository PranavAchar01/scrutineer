# R4 — CoreWeave ARIA, W&B Models, Serverless RL/SFT, Serverless Sandboxes, CoreWeave/W&B Inference: exact surface as of 2026-09-03

All claims below were fetched live on 2026-09-03 from the URLs cited. Anything not fetched is marked UNVERIFIED. Where two sources disagree the discrepancy is stated rather than resolved.

## Summary

- **ARIA is a chat-only agent inside the W&B web/mobile UI.** No API, SDK, or MCP surface for invoking ARIA is documented anywhere on docs.wandb.ai, the W&B MCP server tool list, or the launch press release. It can analyze runs, build panels/workspaces, write W&B Reports, generate sweep configs, keep per-project memories, and — only if you deploy a persistent **W&B Launch queue + agent** — submit experiments. It is Multi-tenant-Cloud-only, team-projects-only, and requires an org admin to enable "Smart features".
- **Serverless RL** = OpenPipe ART (`pip install openpipe-art`, current notebook pins `openpipe-art==0.5.9`) with `art.serverless.backend.ServerlessBackend`, GRPO, and RULER (LLM-as-judge relative rewards, no labels). Training is **free during public preview**; you pay inference tokens + artifact storage. LoRA checkpoints are auto-saved as W&B Artifacts and auto-deployed to W&B Inference under `wandb-artifact:///{team}/{project}/{model}:latest`. The LoRA-servable base models (max rank 16) are: `Qwen/Qwen3.6-27B`, `OpenPipe/Qwen3-14B-Instruct`, `Qwen/Qwen3-30B-A3B-Instruct-2507`, `meta-llama/Llama-3.1-8B-Instruct`, `meta-llama/Llama-3.1-70B-Instruct`. GPT-OSS trainability on serverless is UNVERIFIED (ART's GitHub tagline mentions it; no W&B doc lists it).
- **Serverless SFT** = same stack (`train_sft_from_file()` / `train_sft()` in ART; `POST /v1/preview/sft-training-jobs` on `https://api.training.wandb.ai/v1`), JSONL `messages` (+ optional `tools`), assistant-token-only loss, LoRA persists SFT→RL.
- **Serverless Sandboxes** (`pip install wandb[sandbox]`, `from wandb.sandbox import Sandbox, Secret`) are CoreWeave Sandboxes (Kata VM isolation) rebadged: `Sandbox.run(container_image=..., mounted_files=..., secrets=[Secret(name=...)], network=..., max_lifetime_seconds=...)`, `sandbox.exec([...]).result()` → `stdout/stderr/returncode`, `write_file/read_file`, `Session`/`SandboxDefaults`. Default lifetime 10 min, platform cap 30 days. Public preview, enabled per org (support@wandb.com); Pro plan carries "$25/mo credit for a limited time". GPU sandboxes exist at the CoreWeave policy level (`max_gpu_count`, `gpu_type` runner filters) but W&B docs show CPU-only examples — treat GPU-in-sandbox as UNVERIFIED for the W&B serverless pool.
- **Inference**: one OpenAI-compatible endpoint `https://api.inference.wandb.ai/v1` (CoreWeave Serverless Inference bills at the same per-token table). 26 GA models incl. `Qwen/Qwen3.8-27B`, `openai/gpt-oss-120b` ($0.03/$0.17 per 1M in/out), `deepseek-ai/DeepSeek-V4-Pro`, `zai-org/GLM-5.2`, `moonshotai/Kimi-K2.7-Code`, `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B`. Concurrency caps 2,000/user, 6,000/project; spend caps Free $100/mo, Pro $6,000/mo.
- **W&B MCP server** (`https://mcp.withwandb.com/mcp`, 20 tools) is the programmatic way an agent reads runs/traces/artifacts and writes Reports; it cannot start training, sandboxes, Launch jobs, or ARIA.

## Design implications for the F1 loop

Loop stages: **observe → evaluate → track → document → improve → audit → promote**.

| F1 role | Sponsor surface (verified) | Loop stage it uniquely owns |
|---|---|---|
| **Power-unit engineer** (the engine = weights) | Serverless RL via ART `ServerlessBackend` + RULER; LoRA artifact `wandb-artifact:///team/proj/<role>:vN` served at `api.inference.wandb.ai/v1` (F10, F11, F14) | **improve (weights)** — the only sponsor path that changes a role's *weights*, not just its prompt. Each role that has a trainable LoRA gets its own `art.TrainableModel(name="<role>")`, so "upgrade the power unit" == new artifact version, visibly diffable via `compare_artifact_versions_tool`. |
| **Driver coach / simulator** (SFT warm-start) | Serverless SFT `train_sft_from_file()` on JSONL of best trajectories (F15) | **improve (behaviour cloning)** before RL — distill the winning lineage's traces into the next base. |
| **Wind tunnel / test rig** | Serverless Sandboxes: `Sandbox.run(mounted_files=[harness diff], secrets=[Secret("WANDB_API_KEY")], network=..., max_lifetime_seconds=...)`, parallel `Session` (F19, F20) | **evaluate** — every candidate harness/skill runs in a fresh Kata VM (PARC FERMÉ = the mounted read-only files), one failure stays in one sandbox. Default 10-min lifetime fits a 26-hour hack. |
| **FIA telemetry** | Weave traces (other thread) + W&B MCP `query_weave_traces_tool`, `summarize_evaluation_tool` (F18) | **observe / track** — append-only evidence the improver reads but cannot write. |
| **Race engineer / strategist** | W&B MCP `compare_runs_tool` ("config diff, metric delta"), `diagnose_run_tool`, `get_run_history_tool` (F18) | **improve (proposal)** — credit assignment starts with the config diff + metric delta between generations; the strategist proposes which *role* to upgrade. |
| **Historian / archivist** | W&B MCP `create_wandb_report_tool` (Markdown + panels) + `log_analysis_to_wandb`; ARIA "Build saved views and reports" (F1, F18) | **document** — one Report per generation ("race report"), auto-linked to the artifact versions and runs. |
| **Team principal's analyst** | ARIA chat in the W&B UI (F1–F5) | **document + hypothesis** for the *human*: ARIA is chat-only, so use it live on stage ("Ask ARIA which upgrade mattered most") rather than inside the automated loop. If you want ARIA to *launch* anything, you must run a Docker Launch agent on your laptop (`wandb launch-agent --queue ... --entity ...`, F6). |
| **Scrutineer** | Sandboxes (read-only mounts) + artifact lineage (`list_artifact_versions_tool`, `get_artifact_details_tool`) | **audit** — verify the harness diff against the tampering taxonomy in an isolated sandbox with `egress_mode="isolated"` so the audited agent cannot phone home. |
| **Pit wall / stewards** | W&B Model Registry (`list_registry_collections_tool`) | **promote** — the accepted lineage is a registry collection; BLACK FLAG = version never linked. |

Concrete implications:
1. **Real-vs-simulated boundary**: RL steps on `Qwen/Qwen3.6-27B` show progress "in the first 20-30 steps" over ~2 hours (F10). In 26 hours you can run *one* real Serverless RL job per trainable role (e.g., the power-unit engineer only) and show the LoRA artifact version increment on stage; other roles upgrade via skill-file/prompt diffs evaluated in sandboxes. Budget: training is free in preview; the Qwen3.6-27B rollout tokens cost $0.60/$3.60 per 1M (F8) — 18 rollouts × 20 steps of a few-thousand-token game fits well under $20.
2. **Credit assignment is a first-class artifact**: the strategist must emit a JSON `{role, evidence: [trace_ids], metric_delta}` derived from `compare_runs_tool` output; the upgrade scene reads that file. This makes "why THAT role" auditable (non-negotiable #3).
3. **RULER as the tyre-degradation judge**: because RULER is *relative* within a group (F11), run the same role's N candidate harnesses as one `TrajectoryGroup` and let RULER rank them — no hand-written reward per role.
4. **ARIA is not an API**: do not design a loop stage that programmatically calls ARIA. Give ARIA the "team principal briefing" role (human-in-the-loop document stage) and the demo moment.
5. **Sandbox GPU is unverified**: keep sandbox workloads CPU-only (eval harness, scrutineer checks, marimo notebooks) and route GPU work to Serverless RL/SFT or W&B Inference.
6. **Everything goes through one OpenAI-compatible client**: base models and trained LoRAs share `api.inference.wandb.ai/v1` (F14, F22), so the GHOST CAR (previous generation) and the current car are just two `model=` strings — trivial to race side by side.
